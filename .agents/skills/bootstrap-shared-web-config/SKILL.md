# Bootstrap shared web tooling

Create a real, consumable workspace utility library for ESLint, Prettier, Stylelint, and TypeScript. Support React component libraries, Vite single-page applications, Next.js applications, and browser-oriented standalone TypeScript libraries, including projects that do not use React. Default to browser targets, while correctly handling Next.js server code and Node-based build/config files. Preserve existing project behavior and conventions.

## 1. Inspect and choose versions

- Inspect the workspace root, package manager and lockfile, Node version, `apps/` and `libs/`, existing configs, package scripts, CI, dependencies, and real consumers. Identify framework versions, module formats, CSS syntaxes, TypeScript emit/declaration needs, Node-only files, framework-generated files, and existing config overrides. Keep non-Node projects untouched. Do not overwrite existing configs, rules, commands, or uncommitted work; reconcile their intent and migrate consumers safely.
- Resolve the latest stable versions available at execution time of ESLint, Prettier, Stylelint, framework integrations, and other dependencies actually used. Select TypeScript according to the single-version policy below. Check authoritative package metadata, Node engine requirements, peer ranges, and current upstream documentation; do not hard-code old versions or use prereleases. Use a coherent set and a lockfile produced by the workspace package manager. Report exact versions and any peer/engine conflicts. Never suppress peer warnings, force incompatible versions, or upgrade unrelated frameworks/Node. If a supported combination cannot work, explain the constraint and ask before changing prerequisites. If version metadata or installation is unavailable, report the blocker rather than inventing versions.
- Use the existing workspace package manager; default to pnpm only when present or requested. If there is no workspace, explain the prerequisite and use the workspace bootstrap skill if available and appropriate. Do not create a second workspace or migrate package managers implicitly.

### TypeScript and ESLint compatibility

Use one standard `typescript` package version across the workspace: select the latest stable release supported by the current `typescript-eslint`, framework, build plugins, and existing Node/runtime constraints. Do not use a second compiler, npm aliases, native-preview sidecars, peer overrides, or forced installation to obtain a newer TypeScript. If existing explicit pins conflict, ask before changing them. Verify the same TypeScript version is resolved by `tsc`, ESLint, framework build/typechecking, and development checker plugins. Re-evaluate support at execution time: newer TypeScript may become supported without a compatibility layer. For example, at the time this skill was written TypeScript 7 was outside `typescript-eslint`'s supported peer range, so the latest supported TypeScript 6 release was the single-version choice.

Do not use unconstrained consumer `typescript` dependencies: pnpm can resolve a newer compiler for an app or library while the lint tooling resolves an older supported peer. Declare compatible versions in every relevant consumer and inspect the installed resolutions from each package, not only the shared library.

Prefer `@eslint-react/eslint-plugin` and the official React Hooks plugin for React linting when their current stable peer ranges support the selected ESLint. Its rules are not identical to `eslint-plugin-react`; preserve important existing rules or report behavior differences. `eslint-config-next` can bring in the classic React plugin and `typescript-eslint` transitively even if its own peer range admits a newer ESLint: inspect the full dependency graph. When that bundle conflicts, compose the official `@next/eslint-plugin-next` recommended/Core Web Vitals rules with the shared React and TypeScript presets for Next consumers instead, scoped to their files and root directory. Do not claim this composition is identical to the complete Next config: compare and document rule and accessibility/import coverage, adding compatible supported plugins when needed. Recheck current upstream compatibility at execution time.

## 2. Create the shared library

Use the existing libraries location or `libs/` by default. Create a uniquely named private workspace package, e.g. `libs/web-config` with a scope matching the repository, such as `@repo/web-config`. Add the actual package to workspace discovery. Use an ESM package with an explicit `exports` map for all public config entry points; use real filenames and `workspace:*` dependencies in consumers. Include the packages imported or extended by the library as its runtime `dependencies`, and appropriate tool peer dependencies when needed. Make executables available to the packages that run them; do not rely on pnpm hoisting or undeclared transitive dependencies.

Stylelint resolves string-valued `extends` from its configuration context, which can differ from the shared package under pnpm. Declare the extended config and Stylelint at the locations required by the actual resolution strategy; verify from each CSS consumer without depending on hoisting. If the shared export is an object whose `extends` resolves from the consuming app, make the extended config a direct consumer dependency or use a documented, tested resolution approach.

### Explicit ESLint baseline

For new configurations, use these named upstream flat presets in this order, applying them to the relevant JavaScript/TypeScript files:

1. `@eslint/js` `configs.recommended`.
2. `typescript-eslint` `configs.recommended`, including its parser and TypeScript-aware replacements for core rules. This is the syntax-based preset, not `recommendedTypeChecked`; only enable type-aware rules with a correctly configured per-project TypeScript project service. For example, it enables `@typescript-eslint/no-unused-vars` and disables the conflicting core rule on TypeScript files.
3. For React projects, `@eslint-react/eslint-plugin` `configs.recommended` and `eslint-plugin-react-hooks` `configs.flat.recommended`. Retain the official `react-hooks/rules-of-hooks` and `react-hooks/exhaustive-deps`; disable overlapping `@eslint-react/rules-of-hooks` and `@eslint-react/exhaustive-deps` when present to avoid duplicate diagnostics. Apply Hooks rules to `.js`, `.jsx`, `.ts`, and `.tsx`, including custom Hooks without JSX.
4. For Next projects only, merge `@next/eslint-plugin-next` `configs.recommended.rules` and `configs["core-web-vitals"].rules` with the plugin registered once. Scope to that Next app and set `settings.next.rootDir` correctly for the app/workspace. Include rules such as `@next/next/no-img-element` and `@next/next/no-html-link-for-pages`; no Next rules in ordinary React/Vite or TypeScript libraries.
5. Put `eslint-config-prettier` last in the fully composed consumer configuration so later presets do not re-enable conflicting formatting rules. Prettier formats; don't duplicate formatting rules in ESLint.

These presets are the baseline, not a frozen list: their contents can change with dependency versions. Pin resolved versions in the lockfile, inspect the effective rules with `eslint --print-config` per consumer, and document deliberate local overrides. Preserve existing meaningful rules when adapting projects; do not silently turn off rules other than proven duplicates/conflicts.

Preserve upstream rule severities unless the project explicitly chooses otherwise: an enabled Next rule such as `@next/next/no-img-element` may report a warning without failing ESLint. Verify diagnostics and exit status separately; don't claim every reported violation fails CI.

Provide separately composable, documented entry points for:

| Entry point | Contract |
| --- | --- |
| `eslint/base` | Flat-config JavaScript and TypeScript recommended rules for browser code; browser globals scoped to browser source files and Node globals only for appropriate config/tool files. Exclude generated/build output. |
| `eslint/react` | Base plus React and Hooks rules suitable for both component libraries and Vite SPAs; no Next-only rules. |
| `eslint/next` | Next-specific rules plus compatible TypeScript/React behavior. Compose the official Next plugin's recommended/Core Web Vitals rules with the shared presets when the full Next config has incompatible transitive peers; avoid registering plugins twice or applying Next rules to other consumers. Configure the monorepo app root. Next apps contain server and client code: do not assume all Next source executes in a browser. |
| `prettier` | A shareable Prettier config export; use consistent existing choices or Prettier defaults rather than inventing an elaborate style policy. |
| `stylelint` | A shareable Stylelint configuration for CSS with the current recommended standard rules. Add SCSS, CSS Modules, Tailwind, or other syntax support only when consumers actually need it, with the correct parser/plugins and scoped overrides. |
| `typescript/base.json` | Strict browser-oriented TypeScript base, including appropriate DOM libs. No consumer-specific `include`, `exclude`, `files`, `rootDir`, `outDir`, `references`, or path aliases. |
| `typescript/react.json` | Extends the base with React JSX settings. |
| `typescript/vite.json` | Extends the React config for Vite apps, with bundler-compatible module resolution, isolated transpilation and `noEmit`; consumers provide Vite types where needed. |
| `typescript/next.json` | Next-compatible React settings, preserving framework-required plugin, generated types, and app-specific paths in the consumer where appropriate. |
| `typescript/library.json` | Standalone browser TypeScript library settings, allowing a consumer's existing build and declaration emit strategy rather than globally forcing `noEmit`. |

A library that uses React selects the React preset alongside its appropriate library build settings; do not assume every library is React. Browser defaults must not grant Node globals indiscriminately or break server-side Next files. Make Node-specific type/global support a scoped consumer override, not a blanket restriction on Node files. Use the current `typescript-eslint` recommended flat configs and place `eslint-config-prettier` after conflicting ESLint rules. Keep TypeScript's extended config path resolution in mind: relative paths resolve relative to the file declaring them. For Vite, typecheck separately because Vite transpilation is not typechecking. Do not bake in framework-specific `include`, project paths, build outputs, or a forced emit mode into the shared base.

When a library emits declarations, configure any necessary `rootDir` and output paths in that consumer, not the shared preset. Check the declaration build with the selected TypeScript version; a consumer may need an explicit source root for TypeScript to determine the output layout.

Flat ESLint configuration objects merge globals rather than replace them: adding Node globals in a later matching object does not remove browser globals applied earlier. Scope browser selectors so they do not match Node-only tooling and server files, or explicitly turn off inappropriate globals. Inspect resolved configs for a browser source file, a Node-only config file, and Next server/client files; TypeScript's `no-undef` behavior is not sufficient proof of correct globals.

Next's `"use client"` boundary is not inferred from flat-config filename globs, and server components can import client components. Don't pretend `app/**` or `page.tsx` is uniformly server-only or client-only. Apply scoped boundary rules only where project naming or directory conventions identify the execution environment; document unknown/mixed cases. Where a project explicitly separates `.server.*` and `.client.*`, validate the resolved globals and use appropriately scoped `no-restricted-globals` if enforcing restrictions on TypeScript, because typescript-eslint's recommended preset disables core `no-undef` there. Don't block legitimate Next `process.env.NEXT_PUBLIC_*` usage indiscriminately. Filename-scoped lint restrictions are not a security boundary.

## 3. Connect consumers

- Add thin, valid local entry files and workspace dependencies for each existing matching project: `eslint.config.mjs`, `prettier.config.mjs`, `stylelint.config.mjs`, and `tsconfig.json` extending/importing the appropriate public exports. Compose with necessary existing local overrides instead of deleting them. Only enable Stylelint scripts where styles exist; keep format/lint/check commands non-destructive by default and distinguish fix/write commands. Ensure each actual consumer can resolve the shared package and all tool binaries from its own working directory.
- Create the shared library and all four framework presets even if there are currently no consumers; do not scaffold permanent fake applications just to demonstrate them. Leave existing Vite and Next build configs, React dependencies and TypeScript project references intact unless integration requires a verified change. Do not assume Next is static-only or browsers support Node APIs. Preserve library emit/declaration behavior and package exports; do not add application-only `noEmit` to libraries.
- Provide useful root or per-package scripts for `lint`, `format:check`, `lint:styles` where applicable, and `typecheck`, using existing workspace conventions. Make failure exit statuses propagate. Avoid a recursive root script invoking itself and avoid commands that silently pass when relevant files were not checked. Do not blanket reformat or modify unrelated sources to make checks pass.

## 4. Verify behavior and document

- Install with the selected latest versions and verify the lockfile can be used in a frozen install. Exercise the real package's public exports and consumer config resolution from their own directories. Run ESLint, Prettier check, Stylelint, and TypeScript typechecking through actual consumer commands, plus relevant existing Vite/Next builds and library declaration builds when applicable. A missing consumer is not proof a preset works.
- Repeat formatting checks after builds have produced `dist/`, `.next/`, and other generated output. Ignore only generated artifacts or explicitly select the files to check; don't hide source to make the command pass.
- In a temporary workspace or throwaway fixtures outside the deliverable, exercise **all four** consumer types, including a non-React TypeScript library and a React component library with declaration emit. Include realistic browser code, Vite config code running in Node, Next server/client files, and CSS. Verify clean examples pass, deliberate lint/type/style/format violations fail, a conditional React Hook is flagged in both `.ts` and `.tsx`, and a library can emit declarations. When Vite checker integration is present, verify its actual dev overlay reports both a TypeScript error and an ESLint error, then clears after repair. Start built apps and verify their rendered content in a browser when available. Remove fixtures afterward. If the actual environment, latest-version incompatibility, or framework runtime prevents a scenario, report exactly what was not verified rather than claiming support.
- Update relevant contributor docs with the chosen versions, exported entry points, install and per-consumer examples, scripts, browser versus Node/Next boundaries, framework-specific caveats and override procedure. Confirm existing configs and CI are migrated consistently; report changes, checks actually run, and any blockers.
