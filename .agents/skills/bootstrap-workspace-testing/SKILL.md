# Bootstrap workspace testing

Inspect first, present a project-specific testing plan, and get explicit user confirmation before implementing it. Adapt the actual workspace; do not assume it was created by another skill. Preserve existing projects, tests, scripts, configuration, lockfile, and uncommitted work. Use local dependencies and the repository's pnpm and Node versions, not global installations.

## Style-guide contract

Before proposing test files or test configuration, read this skill's packaged `references/styleguide.md`. Apply its applicable conventions to every generated test and supporting source: domain-first purposeful PascalCase directories and ordinary filenames, named exports and direct imports from defining modules rather than barrels, strict type-first TypeScript with `import type` and narrow documented `any` exceptions, and no runtime cycles. Use the target project's framework-required filenames and exports where they take precedence.

Copy the packaged guide verbatim as exactly one `STYLEGUIDE.md` at the target repository/workspace root, never per package or under `docs/`. If a root guide already exists and differs, preserve it, report the conflict, and ask before replacement. Reference that root guide explicitly from the existing contributor README and root `AGENTS.md`, creating a minimal root `AGENTS.md` only if absent; never duplicate the guide's rules or link generated projects to this skill.

Inspect existing guide locations before copying. If another style guide or package-local copy already exists, do not create a duplicate or delete it; ask how to reconcile or relocate it to the root and update references.

Colocate each unit or React component test with its owning implementation, matching the source basename as `*.test.ts` or `*.test.tsx`. Keep test-only fixtures and helpers next to their owner unless genuinely shared. Exercise observable behavior and mock external boundaries (network, storage, clock, injected services), not internal helpers or component implementation. Keep application E2E suites in a distinct app-level or dedicated E2E area; never place E2E tests in component directories.

When testing setup adds or changes Prettier configuration, use the shared explicit object `{ semi: true, singleQuote: true, trailingComma: 'all', tabWidth: 2, useTabs: false, printWidth: 100, bracketSpacing: true, arrowParens: 'avoid' }` with no import-sorting/order plugin. Reconcile any conflicting existing formatting configuration with the user rather than replacing it silently. Do not introduce lint configuration solely for testing; if approved test setup touches shared/standalone lint, retain its exact baseline: `@typescript-eslint/consistent-type-imports: ['error', { prefer: 'type-imports', fixStyle: 'separate-type-imports' }]`, `@typescript-eslint/no-explicit-any: 'error'`, `import-x/no-cycle: 'error'`, and `import-x/no-self-import: 'error'`.

## 1. Discover projects and existing testing

1. Read the workspace root's `pnpm-workspace.yaml`, package manifests, pnpm and Node pins, lockfile, workspace catalog/settings, scripts, CI, and contributor documentation. Resolve the actual workspace inclusion and exclusion patterns, including nested packages; inspect package names and directories rather than assuming `apps/` or `libs/`. Identify any non-Node projects alongside the workspace and existing commands for them; do not modify them or claim they were tested by pnpm.
2. For each discovered package, inspect its purpose, source and public behavior, dependencies, framework and runtime, module format, TypeScript configuration, build/dev/start commands, and any existing tests, runners, browser tooling, test scripts, fixtures, setup, shared config, CI, and test-only infrastructure. Identify Vite React SPAs, Next apps, React component libraries, browser TypeScript libraries, other Node packages, and existing dedicated E2E packages when present. Do not classify config-only packages or packages without meaningful executable behavior as apps requiring E2E.
3. Record which packages already have coverage and where new tests would add value. Detect existing test infrastructure before proposing another runner or E2E package. Avoid changing or replacing a working suite without discussing a concrete conflict. If there is no pnpm workspace or discovery is ambiguous, explain the evidence and ask how to proceed rather than creating or migrating a workspace implicitly.

## 2. Propose choices and obtain confirmation

Present a concise inventory and a per-project matrix covering its type, existing tests, recommended unit/component, integration, and E2E coverage where relevant, proposed tools, and exclusions. Explain that unit tests target isolated behavior, integration tests exercise collaboration across real components or boundaries, and E2E tests exercise a running application through user-visible flows. Offer the user control over project selection and test layers; do not imply every layer is appropriate for every package.

- Default to Vitest for compatible Vite/React SPAs and TypeScript libraries, and React Testing Library plus user-event for React component behavior where useful. Keep unit/component tests colocated as source-basename `*.test.ts`/`*.test.tsx`; use a DOM environment only for tests that need one and a Node environment for environment-independent logic. Mock only real boundaries, not local implementation details. Reuse existing suitable runners instead of mandating a migration. For different languages or frameworks, propose their native tooling only when relevant and do not install Node test tooling into non-Node projects.
- Evaluate Next apps independently rather than assuming the Vite app's runner is automatically best. Next documents both Vitest and Jest for unit/component tests: Vitest can reduce tooling divergence across a compatible workspace, while `next/jest` supplies Next-specific transforms and mocks for assets, fonts, configuration, and environment files. Prefer an existing suitable runner; otherwise propose the simpler compatible choice for the app's actual imports and test needs, explaining any divergence. Neither currently supports async Server Components as unit tests according to Next's guidance; offer real-app E2E for those flows instead. Check current upstream support when executing, and do not claim a unit-test mock proves server behavior.
- Offer Playwright for browser E2E of runnable Vite or Next applications and cross-package user journeys. E2E exercises applications and their integrated libraries; a utility library or shared configuration package does not automatically need its own browser suite. Choose a minimal browser matrix unless the user requests broader coverage; explain browser installation and CI/runtime costs.
- Where multiple apps or cross-app journeys justify it, offer a dedicated workspace E2E package, potentially shared across multiple apps, versus app-local suites. Discover and prefer an existing suitable E2E package; do not create one solely because multiple packages exist. Describe ownership, how each app is started and targeted, and tradeoffs. E2E dependencies/config/scripts belong to the selected owner, with explicit per-app targets and isolation. Do not make a library package start an unrelated app.
- State what will be added or reused, package locations, proposed scripts, representative real behaviors, compatibility or infrastructure constraints, and any CI changes. Present materially different choices together. If meaningful coverage requires unavailable services, credentials, test data, or a runnable app, identify those prerequisites and alternatives; never invent an API or production credentials.

**Present the discovered plan and wait for explicit user confirmation of the selected projects, test layers, tools, and E2E ownership/location before changing files, installing dependencies, downloading browsers, or modifying CI.** Silence, an unclear answer, or a general request to add testing is not approval of the discovered plan. Ask a follow-up for unresolved choices; if only part is approved, implement only that part and do not infer consent for the rest. Even when the user supplies a preferred selection upfront, check it against discovery and confirm the resulting plan before implementation.

## 3. Implement only the approved plan

1. Check current official documentation and stable package metadata for the selected runners, adapters, framework, Node, pnpm, browser, and existing TypeScript/Vite/React versions. Select current stable compatible versions; inspect actual peer and engine requirements and the dependency graph. Preserve the workspace's single standard TypeScript version where present. Never force incompatible peers, add a second compiler or package manager, or upgrade unrelated projects silently. If constraints require changing prerequisites or the approved design, explain and obtain approval first.
2. Reuse and extend appropriate existing testing configuration and tests. Put each unit/component test beside its owner with the matching `.test.ts`/`.test.tsx` basename; put fixtures/helpers beside those tests unless genuinely shared. Keep test discovery scopes disjoint so Vitest/Jest and Playwright do not collect each other's suites, and keep application E2E in a dedicated app-level or workspace E2E area rather than component directories. Match the project's existing aliases, JSX transforms, environment and module conventions, without replacing Vite/Next build settings. Add shared configuration only when useful to the approved projects and make its consumers explicit; do not assume an existing shared web-config package exports test config or modify it without need.
3. Add noninteractive, failure-propagating per-owner scripts (for example `test`, `test:integration`, and `test:e2e`) for approved layers. Use distinct watch commands only as opt-in. Preserve existing script semantics and do not add empty/no-op suites or recursive root scripts. If adding a root aggregator, select the appropriate packages, avoid invoking itself, and ensure failures propagate. Test commands must not require external services or secrets unless the user explicitly approves and the setup is documented.
4. Add small, deterministic tests of real existing behavior for each approved, testable layer/project: boundaries, observable outputs, state changes, or user journeys, including meaningful error cases where relevant. Prefer user-facing interactions over implementation details. Do not create tautological tests, mock echoes, trivial existence checks, fake application features, or duplicate tests solely to make a suite nonempty. Use isolated data and cleanup; avoid network access, shared mutable state, time-sensitive assertions, and production systems. If a project has no suitable behavior or prerequisites are missing, explain that instead of inventing coverage.
5. For React, use accessible queries and actual interaction for component/integration behavior; limit mocks to real boundaries. For Next, retain server/client boundaries. Check current Next guidance for async Server Components: where the unit runner cannot support them, test the real behavior via an approved runnable-app integration/E2E path rather than pretending a synchronous mock proves it. If E2E was not approved, report the coverage gap.
6. For approved E2E, configure the actual app's supported start command, readiness URL and base URL; provide explicit independent targets for each covered app, with appropriate build prerequisites and ports. Ensure the suite starts/stops only servers it owns, does not accidentally test an unrelated process on a reused port, and works noninteractively in CI. Keep browser binaries, reports, traces and generated artifacts outside source control unless existing policy says otherwise. Protect secrets and avoid destructive data operations. Do not require credentials or external production services by default.
7. Update existing CI only if included in the approved plan; install browser/system dependencies in the documented manner and keep unit/integration and E2E jobs scoped as approved. Do not silently weaken or replace existing checks.

## 4. Verify and document

1. Install with pnpm and validate the updated lockfile with a frozen install when applicable. Confirm actual dependency resolution from each owning package and absence of peer/engine conflicts; do not claim unavailable checks passed.
2. Run each selected project's real noninteractive test command and, for E2E, launch the real selected application and run the browser suite against it. Confirm the intended tests were collected and real user behavior was exercised. Temporarily introduce a deliberate failure in a representative test per configured runner/layer, verify a nonzero exit, restore it, and rerun successfully. Verify root aggregation if added. Run relevant existing lint/typecheck/build commands affected by new configuration, and avoid claiming coverage for unselected projects.
3. Document the actual selected layers and ownership, prerequisites, install/browser setup, per-project and aggregate commands, app startup and ports, CI behavior if changed, and any missing coverage or infrastructure. Record the root `STYLEGUIDE.md` and contributor README/`AGENTS.md` references. Remove throwaway probes and stop owned processes. Report approved versus skipped projects, exact versions and commands run, results, and blockers. If a browser, service, network, or runtime is unavailable, describe the exact unverified behavior instead of presenting a scaffold as working.
