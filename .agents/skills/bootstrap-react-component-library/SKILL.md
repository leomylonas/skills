# Bootstrap a React component library

Create or adapt a real workspace library whose TypeScript/TSX source is imported and compiled by consuming applications. Preserve existing source, public APIs, scripts, configuration, package-manager choice, lockfile, and uncommitted work. Do not add a library bundler, standalone build, generated JavaScript, or declaration build for a new source-only library; the consuming application owns compilation. Do not silently remove an existing library's build, published artifact, or emit contract: explain any conflict and obtain a migration decision.

## 1. Discover the workspace and agree the library's purpose

1. Inspect actual workspace membership, package names and scope, library location, lockfile, Node/package-manager pins, shared config exports, existing apps and libraries, React versions, TypeScript, lint/format/style tooling, CI, and relevant scripts. Default to the established library directory, or `libs/<name>` in a workspace when appropriate. Never infer membership from a directory name; register the package if needed. Do not migrate package managers or affect non-Node projects.
2. Identify requested components, design requirements, styles, supported consumers, and any existing component APIs to preserve. Ask for the intended purpose when no meaningful component behavior is specified and none can be inferred from real existing code. Do not invent a design system, add a demo app, or create placeholder components just to make an export exist.
3. Identify the real target app(s), including Vite and Next when present, their React versions and bundlers, and whether the package is internal source-only or also intended for external publication. This skill targets internal source consumption: if standalone publication is required, explain the incompatible packaging requirement and ask before proceeding.

## 2. Select shared or standalone quality configuration

Discover candidate workspace config packages by their real names, exports, versions, peer ranges, and existing consumers. For shared React library configuration require `eslint/react`, `prettier`, and `typescript/react.json`; require `stylelint` only when CSS will actually be linted. Confirm the React TypeScript preset and any needed library-specific settings work for a source-only library; do not assume a package also provides a composite React/library preset. Explain the proposed changes and ask the user explicitly before referencing a candidate. If no compatible candidate exists, discovery is ambiguous, the user declines, or no answer is available, use the standalone path. Never assume prior consent for another package covers this library.

If approval would conflict with meaningful existing config, identify the exact conflict and ask how to resolve it before replacing behavior. With approval, use the actual package name and public exports, direct workspace dependency, and thin local config files. With standalone config, create equivalent local ESLint, TypeScript, Prettier, and, only for actual CSS, Stylelint configuration. Do not use an application-only Vite or Next TypeScript preset. Keep consumer-specific `include` and any library-specific compiler settings locally; preserve existing project references.

## 3. Resolve and configure the package

1. Select current stable compatible tooling from authoritative metadata, respecting Node engines, peer ranges, workspace framework pins, and the lockfile. Use the one normal TypeScript version resolved by workspace lint, libraries, and apps; no second compiler, aliases, forced peers, or unrelated upgrades. Under pnpm, declare dependencies where imported or run; avoid undeclared transitive dependencies and verify consumer resolutions.
2. Create an internal workspace package with an explicit `exports` map to existing source entry files, including type resolution supported by the actual consumers. Declare React as a peer with a range compatible with intended consumers and as a local development dependency for typechecking; declare React DOM as a peer only if actually imported or required. Add appropriate React type packages locally. Avoid bundling a second React copy. Each consuming app declares a workspace dependency by the real package name. Do not claim direct TypeScript source exports run in untransformed Node or are publishable artifacts.
3. Use strict browser-oriented TypeScript with DOM and React JSX support, bundler-compatible module resolution and `noEmit` for library typechecking. Check actual workspace compiler behavior and preserve consumer aliases/paths. Do not add Vite, Next, a bundler, an app mount, or app-only build scripts to this library. Avoid Node globals in browser components.
4. In standalone ESLint use `@eslint/js` `configs.recommended`, `typescript-eslint` `configs.recommended`, `@eslint-react/eslint-plugin` `configs.recommended`, and `eslint-plugin-react-hooks` `configs.flat.recommended`; keep `@typescript-eslint/no-unused-vars`, `react-hooks/rules-of-hooks`, and `react-hooks/exhaustive-deps`. Disable overlapping `@eslint-react/rules-of-hooks` and `@eslint-react/exhaustive-deps` where present. Apply Hooks rules to `.js`, `.jsx`, `.ts`, and `.tsx`. Use `eslint-config-prettier` last. In the approved shared path use `eslint/react` without duplicate plugin registrations; inspect the effective rules and preserve meaningful existing overrides. Do not apply Next rules to the library.
5. Provide non-destructive `typecheck`, `lint`, and `format:check` scripts, and `lint:styles` only for real supported styles. Exclude generated files, not source. Provide a documented public source entry and real components based on the agreed requirements. Components must have meaningful accessible behavior; use semantic HTML and keyboard behavior where applicable. Do not add unsolicited testing infrastructure; if existing tests apply, retain and run them, or use the workspace testing skill when requested.
6. Support actual consumer boundaries. For Next App Router, put `"use client"` at appropriate interactive component entry modules when they need client behavior, not on the entire library by default; ensure public exports preserve the intended boundary. Avoid server-only imports in client components, and avoid accessing browser globals during module evaluation or server render. Keep server-compatible components server-compatible. Configure `transpilePackages` only where the actual Next version/router/bundler needs it; preserve existing config and verify the consumer rather than assuming behavior. For Vite, verify actual workspace source and CSS resolution. Treat any CSS imports and assets according to the consumer's supported pipeline.

## 4. Verify and document

Install with the workspace package manager and validate the lockfile using frozen/immutable mode when applicable. Run real library `typecheck`, `lint`, `format:check`, and applicable style/test scripts. Check resolved React peers and one TypeScript version. Verify source exports and actual workspace import resolution from every intended existing app; run the affected apps' typechecks and production builds. Start a consumer and exercise the component's actual interaction in a browser when available, including Next server/client rendering when applicable. Use a temporary consumer only when no intended app exists; remove it afterward and report exactly which consumer types were not verified. Prove real component behavior, not merely that an import succeeds. Fix issues in changed files without suppressing diagnostics or reformatting unrelated source.

Document the real package name, source entry points, usage/import example, React peer requirements, supported consumers, client/server boundaries, CSS/asset requirements, selected shared or local config, and actual quality commands. Report exact versions, commands, results, and blockers. Source exports require a compatible consuming toolchain; do not claim a standalone build or universal Node compatibility.
