# Bootstrap a React component library

Create or adapt a real workspace library whose TypeScript/TSX source is imported and compiled by consuming applications. Preserve existing source, public APIs, scripts, configuration, package-manager choice, lockfile, and uncommitted work. Do not add a library bundler, standalone build, generated JavaScript, or declaration build for a new source-only library; the consuming application owns compilation. Do not silently remove an existing library's build, published artifact, or emit contract: explain any conflict and obtain a migration decision.

Use plain CSS Modules (`*.module.css`) for project-owned component and feature styles. Do not introduce SCSS/Sass or project-owned global/non-module stylesheet imports in the library; the consuming app may have at most one app-wide global CSS entry. Non-module CSS required by an installed package or library is an exception; follow its documented import requirements. For existing conflicting styles, preserve behavior, report the conflict and ask before migration; don't silently rewrite unrelated styles.

## Required project conventions

Before generating or changing TypeScript, TSX, CSS, tooling, or project documentation, read this skill's packaged `references/styleguide.md`. Apply it in library source: organize by domain or responsibility with PascalCase directories and ordinary filenames; give substantive components a same-named PascalCase directory and colocate its module CSS, private hooks, private child components, and tests. A standalone `.tsx` file is only for lightweight composition. Keep private children under their owner, promote code only for real feature- or cross-feature reuse, and do not precreate speculative trees.

Generate components as named function declarations and named exports. Define props as `type ComponentNameProps`, accept `props: ComponentNameProps`, and destructure on the first line of the body. Use `type` for ordinary shapes, `interface IName` only for class-oriented contracts, `import type` for type-only dependencies, strict TypeScript, and precise types or `unknown` rather than `any`; allow exceptional `any` only behind a narrow explanatory lint suppression. Use direct relative imports to defining source modules. Never create `index.ts`/`index.tsx` barrels, broad export registries, or a package-root public entry point merely for convenience. Consumers must import direct source modules. If actual package tooling requires an export boundary, expose only precise source subpaths that point directly at defining modules—never a root aggregate, wildcard export, or re-exporting entry file.

Use kebab-case selectors in colocated `Component.module.css` files and camelCase CSS Module access, retaining the plain-CSS/no-SCSS policy above. For every intended Vite and Next consumer, verify the actual CSS Module pipeline and any generated typings map a selector such as `.navigation-item` to a nonempty `styles.navigationItem` class in rendered development and production applications; a typecheck or build alone is not proof. For a Next consumer that lacks this mapping, use a tested selector-aware transformation or another verified compatible solution before generating camelCase access. It must cover project-owned module paths, local versus `:global` selectors, escaped identifiers, native nested selectors, selector lists, and kebab-to-camel collisions, run before CSS Modules, keep typings aligned, and be verified in development and production. Otherwise preserve the selector convention, report the explicit consumer blocker, and do not conceal it behind an unrestricted CSS-module index signature.

Copy the packaged guide verbatim to the target repository/workspace root as `STYLEGUIDE.md`: keep exactly one canonical copy per project/workspace, never a per-package copy. If an existing root guide differs, preserve it, report the conflict, and ask before replacement. Explicitly reference the canonical guide in the existing contributor README and root `AGENTS.md`; create only a minimal root `AGENTS.md` when it is absent, and do not duplicate guide rules in either file. Do not link generated projects to this source skill. Verify the guide file and both references as part of documentation review.

Inspect existing guide locations before copying. If another style guide or package-local copy already exists, do not create a duplicate or delete it; ask how to reconcile or relocate it to the root and update references.

## 1. Discover the workspace and agree the library's purpose

1. Inspect actual workspace membership, package names and scope, library location, lockfile, Node/package-manager pins, shared config exports, existing apps and libraries, React versions, TypeScript, lint/format/style tooling, CI, and relevant scripts. Default to the established library directory, or `libs/<name>` in a workspace when appropriate. Never infer membership from a directory name; register the package if needed. Do not migrate package managers or affect non-Node projects.
2. Identify requested components, design requirements, styles, supported consumers, and any existing component APIs to preserve. Ask for the intended purpose when no meaningful component behavior is specified and none can be inferred from real existing code. Do not invent a design system, add a demo app, or create placeholder components just to make an export exist.
3. Identify the real target app(s), including Vite and Next when present, their React versions and bundlers, and whether the package is internal source-only or also intended for external publication. This skill targets internal source consumption: if standalone publication is required, explain the incompatible packaging requirement and ask before proceeding.

## 2. Select shared or standalone quality configuration

Discover candidate workspace config packages by their real names, exports, versions, peer ranges, and existing consumers. For shared React library configuration require `eslint/react`, `prettier`, and `typescript/react.json`; require `stylelint` only when CSS will actually be linted. Confirm the React TypeScript preset and any needed library-specific settings work for a source-only library; do not assume a package also provides a composite React/library preset. Explain the proposed changes and ask the user explicitly before referencing a candidate. If no compatible candidate exists, discovery is ambiguous, the user declines, or no answer is available, use the standalone path. Never assume prior consent for another package covers this library.

If approval would conflict with meaningful existing config, identify the exact conflict and ask how to resolve it before replacing behavior. With approval, use the actual configuration-package name and its public configuration exports, direct workspace dependency, and thin local config files. With standalone config, create equivalent local ESLint, TypeScript, Prettier, and, only for actual CSS, Stylelint configuration. Do not use an application-only Vite or Next TypeScript preset. Keep consumer-specific `include` and any library-specific compiler settings locally; preserve existing project references.

## 3. Resolve and configure the package

1. Select current stable compatible tooling from authoritative metadata, respecting Node engines, peer ranges, workspace framework pins, and the lockfile. Use the one normal TypeScript version resolved by workspace lint, libraries, and apps; no second compiler, aliases, forced peers, or unrelated upgrades. Under pnpm, declare dependencies where imported or run; avoid undeclared transitive dependencies and verify consumer resolutions.
2. Do not create a package-root public entry point or an `exports` map merely to expose source. Consumers import direct defining source modules using paths supported by their actual workspace toolchain. Only when that toolchain requires an export boundary, add precise source subpath exports that resolve directly to defining modules, including actual type resolution; never add a root aggregate, wildcard export, or re-exporting entry file. Declare React as a peer with a range compatible with intended consumers and as a local development dependency for typechecking; declare React DOM as a peer only if actually imported or required. Add appropriate React type packages locally. Avoid bundling a second React copy. Each consuming app declares a workspace dependency by the real package name. Do not claim direct TypeScript source imports run in untransformed Node or are publishable artifacts.
3. Use strict browser-oriented TypeScript with DOM and React JSX support, bundler-compatible module resolution and `noEmit` for library typechecking. Check actual workspace compiler behavior and preserve consumer aliases/paths. Do not add Vite, Next, a bundler, an app mount, or app-only build scripts to this library. Avoid Node globals in browser components.
4. In standalone ESLint use `@eslint/js` `configs.recommended`, `typescript-eslint` `configs.recommended`, `@eslint-react/eslint-plugin` `configs.recommended`, and `eslint-plugin-react-hooks` `configs.flat.recommended`; keep `@typescript-eslint/no-unused-vars`, `react-hooks/rules-of-hooks`, and `react-hooks/exhaustive-deps`. Explicitly set `@typescript-eslint/consistent-type-imports` to `['error', { prefer: 'type-imports', fixStyle: 'separate-type-imports' }]` and `@typescript-eslint/no-explicit-any` to `'error'`. Register `eslint-plugin-import-x` once, configure its TypeScript parser directly and a verified node resolver for relative TypeScript modules, and enable `import-x/no-cycle: 'error'` and `import-x/no-self-import: 'error'`; `import-x/no-cycle` ignores `import type` cycles. Probe any alias resolver before relying on it, and report CommonJS/dynamic-import analysis limitations rather than treating the rule as complete proof. Disable overlapping `@eslint-react/rules-of-hooks` and `@eslint-react/exhaustive-deps` where present. Apply Hooks rules to `.js`, `.jsx`, `.ts`, and `.tsx`. Use `eslint-config-prettier` last. For a new Prettier configuration, use exactly `{ semi: true, singleQuote: true, trailingComma: 'all', tabWidth: 2, useTabs: false, printWidth: 100, bracketSpacing: true, arrowParens: 'avoid' }`; preserve an existing conflicting configuration and ask before reconciling it. Do not add import sorting or rules not required here. In the approved shared path use `eslint/react` without duplicate plugin registrations; inspect the effective rules and add a narrow override only if the same type-import, `any`, cycle, self-import, parser, or resolver coverage is missing. Its Prettier configuration must use the same explicit options; preserve meaningful existing overrides. Do not apply Next rules to the library.
5. Provide non-destructive `typecheck`, `lint`, and `format:check` scripts, and `lint:styles` only for real supported styles. Exclude generated files, not source. Document the real direct source import paths, never a public root entry, and implement real components based on agreed requirements. Components must have meaningful accessible behavior; use semantic HTML and keyboard behavior where applicable. Do not add unsolicited testing infrastructure; if existing tests apply, retain and run them, or use the workspace testing skill when requested.
6. Support actual consumer boundaries. For Next App Router, put `"use client"` at each direct interactive component module when it needs client behavior, not on the entire library by default; preserve that boundary through any required precise subpath export. Avoid server-only imports in client components, and avoid accessing browser globals during module evaluation or server render. Keep server-compatible components server-compatible. Configure `transpilePackages` only where the actual Next version/router/bundler needs it; preserve existing config and verify the consumer rather than assuming behavior. For Vite, verify actual workspace source and CSS resolution. Treat any CSS imports and assets according to the consumer's supported pipeline.

## 4. Verify and document
Install with the workspace package manager and validate the lockfile using frozen/immutable mode when applicable. Run real library `typecheck`, `lint`, `format:check`, and applicable style/test scripts. Check resolved React peers and one TypeScript version. Verify direct source-module imports and actual workspace resolution from every intended existing app; typecheck actual component props and imports, run the affected apps' production builds, and prove each Vite/Next CSS pipeline maps a kebab-case selector to the generated camelCase key. Start a consumer and exercise the component's actual interaction in a browser when available, including Next server/client rendering when applicable. Use a temporary consumer only when no intended app exists; remove it afterward and report exactly which consumer types were not verified. Prove real component behavior, not merely that an import succeeds. Fix issues in changed files without suppressing diagnostics or reformatting unrelated source.
Document the real package name, direct source import paths and usage example, React peer requirements, supported consumers, client/server boundaries, CSS/asset requirements, selected shared or local config, and actual quality commands. Report exact versions, commands, results, and blockers. Direct source imports require a compatible consuming toolchain; do not claim a standalone build or universal Node compatibility.
