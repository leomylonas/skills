# Bootstrap a TypeScript utility library

Create or adapt a real workspace library whose TypeScript source is imported and compiled by consuming applications. Preserve existing source, public APIs, scripts, configuration, package-manager choice, lockfile, and uncommitted work. Do not add a library bundler, standalone build, generated JavaScript, or declaration build for a new source-only library; consumers own compilation. Do not silently remove an existing build, published artifact, or emit contract: explain any conflict and obtain a migration decision.

## Style-guide contract

Before proposing or generating code, read this skill's packaged `references/styleguide.md`. Apply every applicable rule as a generated-project convention, not merely as advice: use domain-first, purposeful PascalCase directories and ordinary source filenames; keep utilities, their types, and colocated `*.test.ts` files close to their owner; use `type` for ordinary shapes, named exports, explicit relative imports, strict TypeScript, `import type`, narrowly justified `any` suppressions, and no runtime dependency cycles. A PascalCase static utility class is a preferred pattern when it clarifies a utility; a standalone camelCase function in a PascalCase source file is valid when simpler. Keep utilities framework-independent unless their actual behavior requires a platform API. Never create `index.ts` barrels or re-export registries.

Copy the packaged guide verbatim as exactly one `STYLEGUIDE.md` at the target repository/workspace root, never per package or under `docs/`. If a root guide exists and differs, preserve it, report the conflict, and ask before replacing it. Explicitly reference that root guide from the existing contributor README and root `AGENTS.md`; create only a minimal root `AGENTS.md` when absent, and do not duplicate guide rules in either file. Do not add external links to this source skill.

Inspect existing guide locations before copying. If another style guide or package-local copy already exists, do not create a duplicate or delete it; ask how to reconcile or relocate it to the root and update references.

For source-consumed packages, consumers import defining TypeScript modules directly (for example, `@scope/library/src/Currency/CurrencyUtils` for a package without an `exports` map, when that is the actual path). Do not require a root package entry point, `index.ts`, or an aggregate export. Add direct source subpath entries to `exports` only when the selected consumer tooling requires package export maps, and point each entry at its defining source module.

For both standalone and approved shared lint configurations, enforce the exact rules `@typescript-eslint/consistent-type-imports: ['error', { prefer: 'type-imports', fixStyle: 'separate-type-imports' }]` and `@typescript-eslint/no-explicit-any: 'error'`. Permit an exception only with a one-line, nearest-use suppression that explains the unavoidable compatibility boundary; never turn the rule off globally or for a whole file. Use `eslint-plugin-import-x`, not an unverified `import/no-cycle` assumption, for runtime ESM cycle checking: enable `import-x/no-cycle: 'error'` and `import-x/no-self-import: 'error'`. With `@typescript-eslint/parser` as a direct dependency, relative TypeScript imports can use the verified settings `import-x/parsers: { '@typescript-eslint/parser': ['.ts', '.tsx'] }`, `import-x/extensions: ['.js', '.jsx', '.ts', '.tsx']`, and `import-x/resolver: { node: { extensions: ['.js', '.jsx', '.ts', '.tsx'] } }`. The cycle rule ignores TypeScript `import type` declarations, so type-only cycles remain permitted. The node resolver does not resolve aliases or workspace mappings: add a resolver only after verifying its ESLint-version peer graph and test those paths. Do not force the known incompatible ESLint 10 + `eslint-import-resolver-typescript`/`eslint-plugin-import` peer combination. Cycle analysis does not completely discover CommonJS `require` or dynamic-import cycles; keep generated source ESM and state that caveat rather than claiming complete coverage. Confirm the installed plugin with a value-cycle and type-only-cycle fixture before asserting enforcement.

## 1. Discover the workspace and agree the library's purpose

1. Inspect actual workspace membership, package names and scope, library location, lockfile, Node/package-manager pins, shared configuration exports, existing apps and libraries, TypeScript and lint/format tooling, CI, and relevant scripts. Default to the established library directory, or `libs/<name>` in a workspace when appropriate. Never infer membership from a directory name; register the package if needed. Do not migrate package managers or touch non-Node projects.
2. Identify the requested utility domain and actual consumers, including Vite and Next applications when present. Ask for purpose and required behavior when these cannot be inferred from the request or real existing code. Do not invent generic helpers or placeholders just to populate an entry point. Default to browser-compatible, framework-independent logic; distinguish pure utilities from browser-only APIs and do not add React, DOM, or Node dependencies unless actual functionality needs them.
3. Determine whether the library is internal and source-consumed or also needs external publication. This skill targets internal source consumption: if standalone distribution is required, explain the incompatible packaging requirement and ask before proceeding. Preserve existing package APIs and consumers when adapting a library.

## 2. Select shared or standalone quality configuration

Discover existing shared web-config workspace packages by their actual names, exports, versions, peer ranges, and existing consumers. For a candidate require `eslint/base`, `prettier`, and `typescript/library.json`; require `stylelint` only if the library actually owns CSS to lint. Explain the exact package and proposed integration and ask for explicit confirmation before adding a dependency or referencing its exports. If no compatible candidate exists, discovery is ambiguous, the user declines, or no answer is available, use standalone local configuration. Previous consent for another project is not consent for this library.

With approval, use the real public exports, a direct workspace dependency, and thin local configuration entry points. With standalone config, create equivalent local ESLint, TypeScript, Prettier and only applicable Stylelint config; use the explicit shared baseline Prettier object `{ semi: true, singleQuote: true, trailingComma: 'all', tabWidth: 2, useTabs: false, printWidth: 100, bracketSpacing: true, arrowParens: 'avoid' }` and no import-sorting/order plugin. Reconcile an existing conflicting formatting configuration with the user rather than silently overwriting it. Do not require or pretend a shared package exists. Preserve meaningful local overrides and existing project references. If an approved shared preset conflicts with existing behavior, explain the exact conflict and ask how to resolve it before replacing behavior. Do not use React, Vite app, or Next app presets for a framework-independent utility library.

## 3. Resolve and configure the package

1. Select current stable compatible tooling from authoritative metadata, respecting Node engines, peer ranges, workspace framework pins, and the lockfile. Use the one normal TypeScript version resolved by workspace lint, libraries, and apps; no second compiler, aliases, forced peers, or unrelated upgrades. Under pnpm, declare dependencies where imported or run; do not rely on hoisting or undeclared transitive dependencies. Verify consumer resolutions.
2. Keep the package source-consumed: give consumers direct source-module paths, not a mandatory root entry point. Only when the actual consumer resolver requires an `exports` map, expose direct TypeScript source **subpaths** that each name a defining module; do not add `main`, a catch-all export, an `index.ts`, or a re-export registry. Consumers depend on the real package name through the workspace protocol. Do not claim raw source runs in untransformed Node or is a publishable artifact. Do not install React, Vite, Next, or a library bundler as a dependency of an ordinary utility package.
3. Configure strict browser-oriented TypeScript and bundler-compatible module resolution, with `noEmit` for source-only typechecking. Include DOM libraries only if appropriate for the utility's actual APIs; do not add Node global types indiscriminately. Keep library-specific includes and compiler settings in the consumer configuration; do not impose app-only presets or output paths. Preserve existing project references.
4. In standalone ESLint use `@eslint/js` `configs.recommended` and `typescript-eslint` `configs.recommended`, with `@typescript-eslint/no-unused-vars` plus the exact `@typescript-eslint/consistent-type-imports: ['error', { prefer: 'type-imports', fixStyle: 'separate-type-imports' }]` and `@typescript-eslint/no-explicit-any: 'error'` rules, and `eslint-config-prettier` last. Declare `@typescript-eslint/parser` and `eslint-plugin-import-x` directly; register `import-x/no-cycle: 'error'` and `import-x/no-self-import: 'error'` using the verified relative-TypeScript parser/extensions/node-resolver settings in the style-guide contract. Add an alias/workspace resolver only after its peer graph resolves cleanly and its paths are tested; never force the incompatible ESLint 10 resolver graph. Do not substitute `eslint-plugin-import` or claim `import/no-cycle` has the same type-only behavior without verifying the installed rule. Use browser globals only for browser source and Node globals only for relevant config files, accounting for flat-config globals merging. Do not add React, Hooks, or Next rules to ordinary utilities. For the approved shared path use `eslint/base`, verify it enforces the same required rules without duplicate registrations, inspect effective rules, and preserve meaningful existing overrides. Use the shared explicit Prettier object; add Stylelint only for actual supported styles.
5. Provide non-destructive `typecheck`, `lint`, and `format:check` scripts, with `lint:styles` only when appropriate. Exclude generated files, not source. Implement requested real utility behavior with clear types, explicit boundary/error semantics and documented direct public source-module paths; avoid side effects at import time and hidden environment assumptions. Do not add unsolicited testing infrastructure; preserve and run existing relevant tests, or use the workspace testing skill when requested.
6. Verify the actual application's compilation pipeline can consume workspace TypeScript. For Next, consider the actual version/router/bundler and configure `transpilePackages` only when necessary; retain existing configuration. Distinguish browser-only APIs from code safe to call during server rendering, and do not access browser globals at module import merely to make a browser-targeted library work. For Vite, verify actual workspace source resolution. Do not add fictional app consumers.

## 4. Verify and document

Install with the workspace package manager and validate the lockfile using frozen/immutable mode when applicable. Run real library `typecheck`, `lint`, `format:check`, and applicable style/test scripts, and check that TypeScript resolves consistently. Verify source exports and actual workspace import resolution from every intended existing app; run affected app typechecks and production builds. Exercise meaningful utility behavior through a real consumer, including boundary/error cases where relevant, and confirm behavior in a browser if browser-specific. Use a temporary consumer only when no intended app exists; remove it afterward and report exactly which consumer types were not verified. Prove behavior, not just import resolution. Fix changed files without suppressing diagnostics or reformatting unrelated source.

Document the actual package name, direct source entry paths, public APIs and import examples, runtime and browser/server assumptions, supported consumers, selected shared or local config, exact Prettier and ESLint baseline, runtime-cycle checker and its ESM/CommonJS/dynamic-import and alias-resolution caveats, and real quality commands. State that type-only cycles are intentionally excluded and source exports require a compatible consuming toolchain; do not claim a standalone build or universal Node compatibility. Record the root `STYLEGUIDE.md` and its README/`AGENTS.md` references.
