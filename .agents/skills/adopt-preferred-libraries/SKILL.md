# Adopt preferred libraries in existing projects

Augment existing projects according to their actual needs; this is not an application or workspace bootstrap skill. The libraries below are preferred suggestions, not a mandate to install all of them. Discover the workspace and existing implementations first, propose project-specific choices, and obtain explicit confirmation for each library and target project before making changes. Preserve existing behavior, routing, public APIs, configs, tests, scripts, lockfile, package-manager conventions, and uncommitted work unless an explicitly approved migration requires changes.

For React projects, use plain CSS Modules (`*.module.css`) for project-owned component and feature styles. At most one app-wide global CSS entry is allowed for resets, base elements and shared tokens; a component library must not add its own global stylesheet. Do not introduce SCSS/Sass or other project-owned non-module CSS imports. Non-module CSS required by a package or library is an exception, including documented Carbon or Mantine stylesheet imports. Preserve existing conflicting styles and ask before migrating them; do not silently rewrite unrelated code.

## Style-guide contract

Before proposing or implementing an adoption, read the [repository's canonical style guide](../../../STYLEGUIDE.md). Apply its full applicable conventions to generated and modified project code: organise by actual domain/function in purposeful PascalCase directories and ordinary source files; colocate components, private hooks, CSS Modules, tests and private children according to ownership; use named React functions with `type` `<ComponentName>Props`, `props` parameters and first-body-line destructuring; use named exports, direct relative imports to defining modules, `import type`, strict TypeScript, narrow explained `any` exceptions, and no runtime dependency cycles. Do not create `index.ts` barrels, aggregate re-export registries, speculative shared abstractions, or global state merely because a library is being adopted. Framework-required Next files, exports, and CSS locations take precedence.

Implement approved UI changes accessibly by default, including semantic controls, accessible names, keyboard and focus behavior, and accessible errors and states. Call out observed existing accessibility barriers with their location, user impact and a practical remedy; preserve unrelated UI unless a change is approved. Verify affected interactions in a browser and report limitations rather than claiming conformance without assessment.

Responsive behavior is required for approved user-facing changes. Verify affected UI at narrow and wide viewport sizes and relevant intermediate breakpoints, exercising controls and checking clipping/overflow; check zoom or enlarged text where appropriate. Report the viewport sizes and any unverified behavior.

Use CSS Modules for project-owned React component/feature styles, with matching PascalCase module filenames and kebab-case selectors accessed through their exact TypeScript keys, for example `styles['navigation-item']`. Use class-specific declarations or equivalent tooling that rejects misspellings, and keep them synchronized with their source; verify runtime styling in the actual Vite or Next consumer. Preserve Turbopack, the single permitted app-wide global CSS entry and documented vendor stylesheet exceptions.

Copy the canonical guide verbatim as exactly one `STYLEGUIDE.md` at the target repository/workspace root, never per package or under `docs/`. If an existing root guide differs, preserve it, report the conflict, and ask before replacing it. Explicitly reference that root guide from the existing contributor README and root `AGENTS.md`, creating only a minimal root `AGENTS.md` when absent; do not duplicate guide text or link generated projects to this skill.

Inspect existing guide locations before copying. If another style guide or package-local copy already exists, do not create a duplicate or delete it; ask how to reconcile or relocate it to the root and update references.

When an approved adoption adds or changes formatting configuration, use the shared explicit Prettier object `{ semi: true, singleQuote: true, trailingComma: 'all', tabWidth: 2, useTabs: false, printWidth: 100, bracketSpacing: true, arrowParens: 'avoid' }` and no import-sorting/order plugin; reconcile a conflicting existing configuration with the user rather than silently overwrite it. If the approved scope changes shared or standalone lint, retain the exact baseline `@typescript-eslint/consistent-type-imports: ['error', { prefer: 'type-imports', fixStyle: 'separate-type-imports' }]`, `@typescript-eslint/no-explicit-any: 'error'`, `import-x/no-cycle: 'error'`, and `import-x/no-self-import: 'error'`; do not add lint infrastructure merely for a library adoption.

## 1. Inspect the existing workspace

1. Inspect actual workspace membership and package manifests, package names, package-manager and Node pins, lockfile, catalogs, source, build/config files, CI and existing tests. Identify React Vite apps, Next.js apps and their routers, component libraries, utility libraries and non-Node projects. Use real package names and paths; do not infer workspace membership from folder names. Determine where UI components and styling, routing, server-state fetching, validation, forms, date handling, client state, and HTTP requests actually occur, and identify existing alternatives and working integrations.
2. Inspect relevant user journeys and server/client boundaries, API contracts, authentication and authorization, existing request configuration, caching, validation and error semantics, accessibility and date/timezone conventions. Identify real needs and dependencies among choices, without inventing endpoints, data, features, or infrastructure. Do not install React-only packages into framework-independent utilities or alter non-Node projects just to apply a standard. A package can already satisfy a need; distinguish reusable existing integrations from missing ones.
3. Inspect current stable package metadata and official docs for names, APIs, Node engines, React/framework/TypeScript peer ranges, module format and transitive dependencies. Keep the workspace's one normal TypeScript version and existing framework and Node constraints; do not force peers, add a second compiler, silently upgrade unrelated tools or migrate package managers. If the requested library cannot be installed compatibly, identify the issue and ask before changing prerequisites or choosing an alternative.

## 2. Present a plan and confirm each selection

Present a concise per-project matrix with each relevant capability, current implementation, recommended library/version or reason to defer, intended real integration, and any migration/compatibility effects. The preferred choices are:

| Capability | Preferred library | When appropriate |
| --- | --- | --- |
| React UI components | IBM Carbon (`@carbon/react`) or Mantine (`@mantine/core`) | Offer a choice per suitable project; explain design, styling and integration tradeoffs, and allow neither. |
| Client-side routing | `react-router` (and its current documented React integration, if needed) | React SPA with actual navigation; Next.js normally keeps its native router. |
| Remote server-state caching | `@tanstack/react-query` | A client-side server-state need, not a replacement for every server fetch or local UI state. |
| Runtime validation | `zod` | Real input/API boundaries needing schemas; do not mistake a TypeScript type assertion for runtime validation. |
| React forms | `@mantine/form` with Mantine; otherwise `react-hook-form` | Real forms with relevant state or validation; integrate Zod using the selected form library's compatible schema support only when both are approved and needed. |
| Dates | `dayjs` | Actual date/time parsing, manipulation or formatting requirements. |
| Shared client state | `react-granular-store` | Only where TanStack Query and local/context state are insufficient for a demonstrated client-state need. |
| JSON HTTP requests | `@leomylonas/json-fetch-client` | Actual compatible JSON API requests; preserve native/framework-specific fetch semantics when required. |

For each appropriate React project, offer **IBM Carbon, Mantine, or neither** as mutually exclusive default choices; include the existing UI system and any proposed migration in the comparison. Selecting Mantine changes the preferred form library for that project to `@mantine/form` instead of React Hook Form, but still obtain explicit approval before adding it or migrating forms. Separately offer relevant Mantine extras, including `@mantine/hooks`, `@mantine/notifications`, and `@mantine/modals`, plus other current Mantine packages where their capabilities match real needs. Identify required core/peer dependencies separately from optional extras: a dependency required by an approved package must be disclosed as part of that package's approval, while optional features need their own approval. Selecting Mantine alone does not approve all extras or a form migration.

A valid plan can recommend different libraries for different projects or no new dependency for a given capability. Explain alternatives already present, conflicts, provider locations, affected behaviors and tests, new dependencies, and migration risks. Present related choices together, but ask for **explicit approval for each library and target project**, including whether to adopt it for new usage only or migrate specified existing code. For related selections, make dependencies explicit: e.g. a Zod form resolver needs approval for both libraries and the resolver. Confirmation of one library or a blanket request to apply preferences does not approve every listed integration or replacement. Silence, ambiguity, or an unconfirmed item means do not implement that item; proceed only with separately approved choices. Ask follow-up questions for material unresolved choices before changing the affected area. A user may approve multiple explicitly identified items in a single response.

Do not replace a working UI, routing, request, cache, validation, form, date or state implementation merely because a preferred alternative exists. An approved migration must specify its scope and preserve existing behavior and callers; do not create parallel overlapping systems without a justified transition. If there is no real use for an approved library, explain the gap rather than adding a dependency, fake endpoint, placeholder provider, or demo feature. Do not add dependencies to every package when only one consumes them.

## 3. Integrate only approved selections

1. Install latest stable versions compatible with the actual workspace, subject to existing pins and approved changes. Declare direct runtime dependencies in each package that imports them and peer dependencies where appropriate for reusable libraries. Preserve pnpm strict resolution and lockfile semantics. Respect shared config and source-consumed workspace package conventions. Do not globally install tools, override peer constraints, introduce duplicate React copies, or use fabricated APIs.
2. **Routing:** For a React SPA, follow the selected version's official React Router API and integrate with the existing entry point and hosting/deep-link requirements. Preserve paths, search parameters, redirects, history, accessible navigation and existing route behavior. Do not insert a second router into Next or replace its file-based router unless the user explicitly requests and approves a viable architecture.
3. **Server state:** Integrate TanStack Query only around actual client-side fetching with a correctly scoped `QueryClient` and provider. Preserve loading, error, cache and mutation/invalidation semantics and handle request cancellation where supported by the real request API. In Next, observe client/server boundaries, avoid module-global server caches shared across users, and follow current hydration/SSR guidance if used; do not convert server components unnecessarily.
4. **Validation and forms:** Place Zod schemas at real input or API boundaries; validate unknown data and surface meaningful errors. With Mantine selected, use approved `@mantine/form` for actual forms instead of introducing React Hook Form; otherwise prefer approved `react-hook-form`. Preserve defaults, accessibility, submission behavior, focus and error messages. For Mantine plus Zod, use the selected Mantine version's documented schema integration (current versions support Standard Schema via `schemaResolver`); choose sync validation only for synchronous schemas. For React Hook Form, use `@hookform/resolvers` only if both schema/form integration and that supporting dependency were approved or explicitly included in the approved plan. Do not silently replace or remove an existing form library without a separately approved migration; report an incompatible existing form setup rather than introducing competing form systems. Never log sensitive input or duplicate incompatible schemas without need.
5. **Dates:** Use Day.js only for actual date operations, respecting existing locale, timezone, validity and formatting semantics. Add only necessary official plugins and verify UTC/timezone behavior where relevant. Do not replace date-only values with local-time instants or change serialized formats silently.
6. **Client state:** Prefer existing local or context state for simple UI state and TanStack Query for remote data. Only add `react-granular-store` for the approved, demonstrated shared client-state need. Follow current documented APIs, scope store instances to the appropriate component/provider/request lifetime, and prevent cross-request or cross-user leakage in SSR/Next. Preserve existing state transitions; do not duplicate server-state caches in the store.
7. **JSON API:** Use `@leomylonas/json-fetch-client` for approved compatible JSON requests following the installed version's API. Preserve base URLs, relative/root-relative/absolute path semantics, credentials, headers, request bodies, errors and cancellation supported by the client. The documented client treats `/path` as root-relative rather than prefixing its configured base URL; verify actual URLs instead of guessing. A root-relative URL can work in the browser but fail in Node's `fetch`, which has no browser document origin; use a correctly resolved absolute URL for server requests where needed. A generic type parameter alone is not runtime validation; use an approved schema where validation is required. Account for non-JSON/204 responses and framework fetch caching/revalidation, streaming, or server request context when relevant; do not migrate an incompatible request silently. Never expose server-only tokens or configuration in client bundles.
8. Keep providers, schemas, stores and request clients as simple and local as their actual scope permits. Use direct imports from each defining module rather than barrels; define types near their owner and promote them only when genuinely shared. Don't create an abstraction library, speculative `Shared` tree, DI container, or unrelated features. Preserve Next server/client boundaries and source-consumed library public contracts. Adapt existing tests when behavior or APIs intentionally change; add permanent colocated `*.test.ts`/`*.test.tsx` tests only for meaningful consumer-visible transitions, errors, boundaries or regression risks using existing conventions.

**UI system:** For approved Carbon, follow current `@carbon/react` installation, peer, style and theming guidance; integrate actual components without replacing the project's design system outside the agreed scope. For approved Mantine, follow current framework-specific documentation for compatible `@mantine/core` and required peers, core/extra CSS import order, `MantineProvider`, theme and SSR/color-scheme setup. Add approved extras such as notifications or modals with their documented styles and providers only where actual use warrants them; hooks may also be required as a core peer. Use matching compatible Mantine package versions. Preserve Vite/Next server/client boundaries and existing styles, accessibility, and responsive behavior. Do not add Carbon and Mantine together by default, install an extra just because it was offered, or replace existing components without approved migration.

## 4. Verify and document

Install with the repository package manager, then validate the updated lockfile using frozen/immutable install when applicable. Inspect the resolved versions, peer dependencies and any framework/Node constraints. Run affected projects' actual lint, typecheck, tests and production builds; preserve failure exit statuses. Exercise each approved integration through the real affected path: navigation/deep links, query loading/error/mutation states, validation and accessible form submission, date edge cases, shared-state updates, and JSON request/error behavior as applicable. Use a local disposable HTTP fixture for API verification if a real safe endpoint is unavailable; never use a fabricated production endpoint or live credentials. For browser UI, load the actual app and exercise affected behavior in a browser when available. In SSR paths verify request/user isolation and server/client behavior where relevant. Remove temporary fixtures and stop owned processes.

For an approved UI system, exercise the actual components, keyboard/focus and responsive behavior in a browser; verify theme and styles load. For Mantine, also exercise each approved form, notification or modal integration and check SSR/hydration where the app uses it. Report any missing browser or SSR verification.

Document the choices actually implemented, dependencies, configuration, commands, and any behavior or migration implications in existing project documentation. Record the root `STYLEGUIDE.md` and its contributor README/`AGENTS.md` references. Report approved versus skipped recommendations, exact versions and checks actually run, remaining conflicts and unverified paths. If network, runtime, API contract, credentials, or a required server is unavailable, report the specific blocker rather than claiming integration works.
